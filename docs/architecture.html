Architecture · POD_Verifier × sarathy

Proof‑of‑Delivery Scoring

Every delivery photo a rider uploads is scored by an EfficientNet model for whether it actually shows the parcel, at the door, legibly. Two services, one writer, and a set of deadlines built around the fact that the photo is usually not in S3 yet when we first look for it.

Scorer POD_Verifier · AWS Lambda Owner of record sarathy · Spring Boot Region ap-south-1 (prod) · us-east-2 (stage)

01 — The boundarySarathy owns the data. The scorer owns the model.

“It is not a right thing to have 2 sources to modify the database belonging to a particular service.”

The rule this architecture exists to satisfy

The Lambda used to hold credentials to sarathy's Postgres, run its own DDL and write pod_scores itself. It no longer carries a database driver at all — the image build fails if one reappears in requirements.txt. It asks sarathy what to score over HTTP and posts back what it found.

That makes sarathy the only writer to its own schema, and it puts every decision that depends on the data — which links already carry a score, which failures are due another attempt, which photos have been replaced — on the side that owns the data. The scorer decides one thing: what the image looks like.

The four /internal/pod-scoring endpoints are reachable only inside the VPC, over the internal NLB, with no app-level token. That is deliberate and it is why they are namespaced /internal: a public address would expose an unauthenticated write to pod_scores. provision-stack.sh refuses to deploy a SARATHY_BASE_URL that resolves publicly.

02 — Entry pointsThree ways in, one scoring path

All three converge on score_and_record: download a window of images concurrently, run inference in batches, post every outcome back. A failed download is recorded as a row, never dropped.

Per trip · two call sites

One trip, immediately

Sarathy invokes asynchronously from two places, in order: a POD verification request while the trip is still open and a TL is about to judge it, then completion. Neither fires when every link already carries a score. Latency-sensitive — this is why containers are kept warm.

Verification comes first, and that is the score that matters

The POD verification flow exists because a rider without the delivery OTP cannot close the trip themselves. They upload the photo, raise a request, and a TL approves or rejects it — and only then does the app call /app/complete. verifyPod states the ordering in code by refusing outright when the trip is already COMPLETED.

So the verification request is the latency-critical score: the trip is still open, a person is about to make an approve/reject call, and the point is that the model's opinion is on screen when they do. That is what the warm pool is for.

Completion is the later, quieter trigger, and it carries two jobs. It is the only per-trip score for the ordinary flow, where the rider has the OTP and never raises a request at all. And in the verification flow it is normally a no-op — the request already scored these links — firing only when the POD changed in between, which is exactly the case of a TL rejecting and the rider re-uploading.

Sarathy checks before it invokes: if every link it would send already carries a score, it skips the call rather than spending an invocation to be told so. The check runs through the same tripForScoring the Lambda itself would consult, so the two cannot disagree about what “already scored” means. It deliberately fails open — any doubt and the invoke goes out, because scoring twice costs one invocation and an idempotent upsert, while not scoring at all costs a photo nobody ever looked at.

What the sweep covers, and what it doesn’t

The sweep selects on status = 'COMPLETED'. For completed trips it is a complete safety net — a dropped, throttled or Lambda-down invoke costs nothing but half an hour — which is why both per-trip call sites swallow their failures without touching the rider's response. Eight code paths set a trip to COMPLETED and only lmtripCompleteProcess invokes; the rest are pickup placeholders and tour closures that carry no photo.

A trip sitting in REQUESTED is outside that net. It is still open, so the sweep cannot see it, and the verification-request invoke is the only thing that will score it before it closes. Losing that invoke loses nothing permanently — completion or the sweep picks it up afterwards — but the TL decides without a score, and that failure shows up as a worse decision rather than as a missing row.

Why the sweep window is 26 hours and not “today”

A run at 23:30 asking for today covers up to 23:30. Every trip completing between then and midnight would fall into no run at all, because the next day's runs look at the next day's timestamps. A rolling window longer than a day has no such seam, costs nothing extra — sarathy reports which links already carry a score — and re-covers any run that failed or was throttled.

Why the window is on updated_at and not closed_at

Two reasons. Trip.onUpdate() is a @PreUpdate callback, and completing a trip is an UPDATE, so a trip that completed inside the window necessarily carries an updated_at inside it — the guarantee is structural rather than a convention each of the eight call sites has to remember. And a POD can be replaced after completion: FmMmTourTripService.completeTrip's already-COMPLETED branch writes new URLs and bumps updatedAt while deliberately leaving closedAt alone. A closed_at window would never look at that trip again.

03 — The sequenceThe life of one POD link

This is a real sequence and the ordering carries the design. Steps 04 and 07 are where the system's two genuine hazards live.

  1. The rider finishes a delivery
    Rider app

    Photos are queued for background upload to S3 and presigned URLs are generated locally.

  2. The app announces the URLs
    Rider app → sarathy · POST /app/save-info

    SpmdTripService.tripInfoPopulator writes trip.pod from the request body verbatim. The server never touches S3 and never checks that the object exists.

  3. No OTP: the rider asks a TL to check the photo
    sarathy · POST /trip/send-pod-verification

    podVerificationStatus = REQUESTED, TLs are notified, and the scorer is invoked. The trip is still open — the sweep cannot see it — so this invoke is the only thing that scores it before the TL decides.

  4. The trip completes
    sarathy · POST /app/complete

    Called on TL approval, or directly when the rider had the OTP all along. updated_at is stamped and the trip enters the sweep's window. A per-trip invoke fires too — unless every link already carries a score, which in the verification flow it usually does.

  5. The scorer asks S3 for the image — and it may not be there
    Lambda · the upload race

    A 403, a 404 or a suspiciously short body almost always means the upload is still in flight, not that the link is dead. The download retries in place at +5s then +15s, bounded by the invocation's deadline. A timeout or a 5xx is not retried here — that is the host being unwell, and the HTTP adapter already handles it at the socket level.

  6. Inference
    Lambda · EfficientNet, four heads

    context_valid, package_visible, label_readable, image_clarity, combined by fixed weights into pod_score. ImageNet normalization is mandatory — it is the correctness fix the model was retrained around.

  7. Results are upserted
    Lambda → sarathy · POST /scores

    Idempotent on (awb, pod_link, run_date), so a retried invocation updates rather than duplicating. A success clears the retry schedule; a failure advances it.

  8. Replaced photos are retired
    sarathy · supersede reconciliation

    The same write reconciles each named trip against its current trip.pod. Any score row whose link is no longer part of the POD is stamped superseded_at and drops out of pod_scores_flagged.

  9. Anything still missing comes back round
    sarathy schedule · Lambda retry pass

    Attempts at +30m, 1h, 2h, 4h, 8h, 16h, stopping 24 hours after the first failure — which is when the app's own background upload task abandons the image, so past that point nothing is left to arrive.

04 — The upload raceMost “failures” are a photo that hadn’t landed yet

trip.pod is filled from URLs the client generated, at the moment the client said so. The bytes follow on the rider's connection. Essentially every download_failed row in pod_scores is that gap, which is why the system treats a failure as a schedule rather than a verdict.

A flat 5–10 second sleep on every invocation was considered and rejected: it would pay the wait for the ~90% of images already present, and delay every rider's answer to help the few that are not. Retrying only the links that actually miss costs nothing in the healthy case.

Bounding it by attempts, not by age

An uncapped retry set grows without limit — a few hundred permanently dead links a day becomes six figures within a year, and every 30-minute run would try all of them. Bounding by attempt count with widening gaps keeps the cost flat while still giving a slow upload most of a day to arrive.

05 — Replaced photosSuperseding, per link and never per trip

/app/save-info replaces trip.pod wholesale, so a re-upload leaves the previous link's row behind. pod_scores_flagged takes MAX(pod_score) across every row for an (awb, run_date) — so a rider who replaced a good photo with a bad one still read PASS, decided by an image that is no longer the POD.

A row is superseded if and only if its link is absent from the trip's current POD. Nothing about the trip having been updated retires anything by itself, which is what makes the common additive re-upload safe.

[A, B] → [A, B, C]
Nothing retired. A and B are still the POD; C is simply new.
[A, B] → [C, D]
A and B retired. A full replacement.
[A, B] → [A, C]
B retired only. A survives untouched, C is new.
[A, B] → [A, B]
Nothing retired, nothing inserted. The upsert just refreshes the rows.

The current link set is read from the database at write time, not taken from the scorer's payload — the payload can be seconds stale, having been built before a re-upload that has since landed.

06 — The incidentWhy the reads look the way they do

Production · every run, silently

The first version of the sweep filtered on COALESCE(closed_at, updated_at) and paginated on trip_id. Filtering one column and ordering by another cannot be served by an index, so the planner walked the primary key upward from the lowest trip id, testing each row. Production ids are past 50.7 million and the wanted rows are all at the top.

Every run hit statement_timeout — SQLState 57014 — on all four of the scorer's attempts, every thirty minutes, having scored nothing. It was never seen in staging, where the trip table is small enough that walking it is instant.

The expression could not have been indexed either: closed_at is timestamp and updated_at is timestamptz, so the COALESCE resolves through an implicit cast that reads the session TimeZone — making it STABLE, and Postgres will not index a non-immutable expression.

The fix filters and orders on the same tuple, (updated_at, trip_id), compared as a row value. It needs no new index — trip.updated_at is already indexed, which a planner probe through the Metabase FDW confirmed before a line was written.

The cursor carries microseconds

Postgres timestamps resolve to microseconds. A cursor truncated to milliseconds compares below the row it came from, so that row is served again — and a page whose rows all share one millisecond never advances the cursor at all. The fourth measurement above is that loop, reproduced on a table seeded so thousands of trips share a millisecond, as production does. The token is opaque to the scorer: echo it back, never parse it.

08 — Operating notesDeploying, tuning, watching

Order matters

Sarathy first, with its migration and API in the same artifact, then the Lambda — the scorer calls /retry-links, which does not exist until sarathy ships. Keep the EventBridge schedule disabled until both sides are up. SARATHY_BASE_URL must be set in the CircleCI context and must not resolve publicly.

Dials worth knowing

SWEEP_LOOKBACK_HOURS26Must stay above 24 or the midnight seam reopens.

What to watch

CloudWatch namespace PODPipeline carries ImagesScored, ImagesFailed and ImagesUncovered; uncovered should be zero, since every input gets an outcome. In the logs, the sweep's recovered against attempted says whether retrying is earning its keep, and the recovery histogram says whether 24 hours is the right cutoff. A run reporting continuing queued a bounded continuation and will resume itself.

Known limits

A POD replaced more than 26 hours after the trip was last updated needs a manual retry_failed event. A link that only lands after the 24-hour cutoff is never scored automatically. Neither is a bug; both are the deliberate edge of a bounded system, and both are reachable by hand.
